# w312 re-research

## Decision

**AGREE** with the disagreement memo. Recommended primary verdict: `EVIDENCE_GAP`. Recommended review verdict: `CORRECTION_REQUIRED`.

The vulnerability, atomic BIC, immediate-parent absence, PR-member decomposition, affected Git interval, and direct fix all close. The original `NOT_AI` verdict does not: the BIC records only the placeholder identity `Your Name <you@example.com>`, and GitHub associates that email with `invalid-email-address`, not with the PR submitter. Absence of an AI marker is not positive evidence of a named human writer. This is the object-quality exception described by the disagreement memo, not a general “no trailer means gap” rule. The BIC object and GitHub rendering are available at [ef52453de9523f6a010652847b61cb340ed5daa5](https://github.com/hashcat/hashcat/commit/ef52453de9523f6a010652847b61cb340ed5daa5), and the containing PR is [hashcat/hashcat#4471](https://github.com/hashcat/hashcat/pull/4471).

## Vulnerability mechanism

Commit [ef52453de9523f6a010652847b61cb340ed5daa5](https://github.com/hashcat/hashcat/commit/ef52453de9523f6a010652847b61cb340ed5daa5) first adds `src/modules/module_34301.c`. Its `keepass4_t` has `header[64]`, a 256-byte destination; token 9 accepts 400–600 hexadecimal characters; and `module_hash_decode()` halves that token length and calls `hex_decode()` without checking the destination size. A maximal token therefore decodes 300 bytes into 256 bytes: 44 bytes past `header`, ending at byte 336 of a 328-byte esalt and thus writing 8 bytes beyond the allocation.

This source-level replay matches the maintainer's runtime replay: 512 hex characters stay in bounds, 514 overwrite the following esalt field, 586 trigger glibc heap-corruption detection, and 600 trigger SIGSEGV. The maintainer explicitly confirmed the finding as valid in [hashcat/hashcat#4737](https://github.com/hashcat/hashcat/issues/4737#issuecomment-5307564219). The published [CVE-2026-68765](https://www.cve.org/CVERecord?id=CVE-2026-68765) and [GHSA-jfqq-rfm8-8frm](https://github.com/advisories/GHSA-jfqq-rfm8-8frm) describe the same 600-hex-to-300-byte decode into a 256-byte buffer.

## Atomic BIC and immediate parent

The atomic BIC is [ef52453de9523f6a010652847b61cb340ed5daa5](https://github.com/hashcat/hashcat/commit/ef52453de9523f6a010652847b61cb340ed5daa5), a normal single-parent commit whose sole parent is [9212532dec54a286cf3b8bac281bb6fa26e540aa](https://github.com/hashcat/hashcat/commit/9212532dec54a286cf3b8bac281bb6fa26e540aa). Local `git log --all --reverse -S 'token.len_max[9] = 600' -- src/modules/module_34301.c` returns only `ef52453de9523f6a010652847b61cb340ed5daa5` adding the bound and [6f374c4ff7d5dc951530fbbbcf6b45e3c169b100](https://github.com/hashcat/hashcat/commit/6f374c4ff7d5dc951530fbbbcf6b45e3c169b100) removing it.

The immediate-parent tree has no `src/modules/module_34301.c` and no `token.len_max[9] = 600`. Its sibling `src/modules/module_34300.c` fixes token 9 at 506 hex characters, which decodes to 253 bytes and fits its 256-byte `header[64]`. Thus the BIC simultaneously first writes the vulnerable 600-character allowance, fixed 256-byte destination, and unchecked decode; it is not a move, refactor, revert, merge, or later repair.

## Squash or member decomposition

The vulnerable branch entered master through ordinary merge [b1251dd4401726bbd0c9da2d6880c45d5eea8b27](https://github.com/hashcat/hashcat/commit/b1251dd4401726bbd0c9da2d6880c45d5eea8b27), not through a squash. [PR #4471](https://github.com/hashcat/hashcat/pull/4471) exposes exactly three branch members: BIC `ef52453de9523f6a010652847b61cb340ed5daa5`, merge-from-master `ac267a19287ca64c3055129c3aec1ac23c05ba1d`, and repair `52f9dae0bf076e3b127bb69cf78c60c3e7bdeb6e`. A local diff from `ef52453de9523f6a010652847b61cb340ed5daa5` to `52f9dae0bf076e3b127bb69cf78c60c3e7bdeb6e` for `src/modules/module_34301.c` is empty, so neither later member rewrites the flaw.

The fix has the opposite shape. [PR #4755](https://github.com/hashcat/hashcat/pull/4755) has direct patch [34ed9220e90b0d1c3b361d436abb213a15449be9](https://github.com/hashcat/hashcat/commit/34ed9220e90b0d1c3b361d436abb213a15449be9), parent `e166d928b4a85d5582d3539536b016d9eee0ffbc`, which was squash-landed as [6f374c4ff7d5dc951530fbbbcf6b45e3c169b100](https://github.com/hashcat/hashcat/commit/6f374c4ff7d5dc951530fbbbcf6b45e3c169b100), parent `c8f1bf3e828a86612d315bfbe7951e72c882be9b`. The PR-head object is not an ancestor of the squash, but both diffs have stable patch-id `ab9f0e771d438ab30f3c195869ad6234d0f88b41`.

## Affected and fixed releases

The current CNA record gives the affected Git interval as `ef52453de9523f6a010652847b61cb340ed5daa5` inclusive through `6f374c4ff7d5dc951530fbbbcf6b45e3c169b100` exclusive; see [CVE-2026-68765](https://www.cve.org/CVERecord?id=CVE-2026-68765). Tag [v7.1.2](https://github.com/hashcat/hashcat/releases/tag/v7.1.2) resolves locally to `c75f446c44cd3f0742035a1394416c39bee5ea8f`, is an ancestor of the BIC, and has no `src/modules/module_34301.c`.

In the audited clone, `git tag --contains` returns no tag for either `ef52453de9523f6a010652847b61cb340ed5daa5` or `6f374c4ff7d5dc951530fbbbcf6b45e3c169b100`. The maintainer independently states that the vulnerable module was added after v7.1.2 and never appeared in a release in [hashcat/hashcat#4737](https://github.com/hashcat/hashcat/issues/4737#issuecomment-5307564219). Therefore the affected builds were master snapshots only; no tagged release was affected, and the fix was not yet present in a tagged fixed release in the refs audited on 2026-08-30.

## Direct fix or unpatched state

The direct landed fix is [6f374c4ff7d5dc951530fbbbcf6b45e3c169b100](https://github.com/hashcat/hashcat/commit/6f374c4ff7d5dc951530fbbbcf6b45e3c169b100). It reduces token 9's maximum from 600 to 512 hex characters and adds a pre-decode rejection when `header_len > sizeof (keepass4->header)`, closing both the tokenizer bound and the sink-side bound. [PR #4755](https://github.com/hashcat/hashcat/pull/4755) confirms that the old 600-character allowance exceeded the host and kernel buffer capacity and that the fix was merged to master.

Earlier commit [bc33157eb23411e50f1e96a69dc837021d14ec12](https://github.com/hashcat/hashcat/commit/bc33157eb23411e50f1e96a69dc837021d14ec12) adds only `if (line_len < 128) return (PARSER_SALT_LENGTH);`; it leaves token 9's 600-character maximum and unchecked `hex_decode()` unchanged. It is not a direct fix for this path.

## BIC-only AI attribution

Raw object `ef52453de9523f6a010652847b61cb340ed5daa5` is unsigned and records author and committer as `Your Name <you@example.com>`. Its entire message is `implement keepass4 aeskdf`; it has no `Co-Authored-By`, `Signed-off-by`, generator, bot, or AI trailer. GitHub's [commit API](https://api.github.com/repos/hashcat/hashcat/commits/ef52453de9523f6a010652847b61cb340ed5daa5) and [commit page](https://github.com/hashcat/hashcat/commit/ef52453de9523f6a010652847b61cb340ed5daa5) associate the placeholder email with the generic account `invalid-email-address`.

These facts establish no positive AI marker, but they also do not establish a named human writer. Although [PR #4471](https://github.com/hashcat/hashcat/pull/4471) was submitted from `thatux:keepass4`, PR ownership is external to the BIC object's author identity and cannot substitute for BIC-only attribution. The BIC therefore supports neither `AI_CONFIRMED` nor `NOT_AI`; fail-closed treatment is `EVIDENCE_GAP`.

- Set review verdict to `CORRECTION_REQUIRED`.
- Preserve the primary findings for vulnerability mechanism, BIC `ef52453de9523f6a010652847b61cb340ed5daa5`, parent `9212532dec54a286cf3b8bac281bb6fa26e540aa`, merge decomposition, Git affected interval, and direct fix `6f374c4ff7d5dc951530fbbbcf6b45e3c169b100`.

## Remaining gap

No admissible BIC-only evidence ties `ef52453de9523f6a010652847b61cb340ed5daa5` to a named human authoring process or supplies a positive AI/bot/generator marker. The PR submitter and branch ownership do not close that object-level attribution gap. Unless such evidence becomes available, the causal writer remains `EVIDENCE_GAP`.
