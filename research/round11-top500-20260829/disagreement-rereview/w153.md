## Vulnerability mechanism

With access control enabled, the vulnerable flow normalizes the request lexically and then performs a prefix containment test. At tag `v1.8.0` (commit `babe0c817cd389d165c526942febc7806f0c9a42`), `to_abs_path` returns `os.path.normpath(path)`, `is_path_trusted` accepts `path.startswith(parent_path)`, and `/file` calls `check_path_trust(path)` before returning `FileResponse(filename)` for the original path. `normpath` does not resolve a symlink, while the file sink does. The [CVE record](https://www.cve.org/CVERecord?id=CVE-2026-77815), [GHSA](https://github.com/advisories/GHSA-cw66-pfp5-82xp), and [reporter's reproduction](https://github.com/zanllp/infinite-image-browsing/issues/968) describe the same CWE-59 source-to-sink mechanism.

I replayed the primitive without writing a fixture: with allowed parent `/proc/self`, request `/proc/self/root/etc/passwd`, `normpath` remains `/proc/self/root/etc/passwd` and passes the old prefix check, the existing `/proc/self/root` link resolves the sink target to `/etc/passwd`, and the fixed `realpath(parent) + os.sep` comparison rejects it. This is a non-inferential reproduction of lexical acceptance followed by link resolution.
