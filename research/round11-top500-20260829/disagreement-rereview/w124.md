# w124 re-research

## Decision

**AGREE** with the disagreement memo. Recommended primary verdict: `EVIDENCE_GAP`. Recommended review verdict: `CORRECTION_REQUIRED`.

The vulnerability, affected releases, and direct fixes are verified, but `691a9df5a0aff0dddeedc5181f6e5832ee90dcea` is an incomplete mitigation, not the atomic bug-introducing commit (BIC). Its immediate parent is already vulnerable, and the actual first writer is not closed to a permitted atomic public object. Therefore `NOT_AI` is not supportable under the audit protocol.

## Vulnerability mechanism

Apache's CNA record says that CVE-2026-42778 is the failure to apply the CVE-2026-41409 fix to the 2.1.X and 2.2.X branches: the CVE-2024-52046 classname allowlist was applied only after a class static initializer might already execute, and affected applications are those calling `IoBuffer.getObject()` ([Apache CNA CVE record](https://github.com/CVEProject/cvelistV5/blob/main/cves/2026/42xxx/CVE-2026-42778.json); [GHSA-995c-6rp3-4m4x](https://github.com/advisories/GHSA-995c-6rp3-4m4x)).

Replaying tag `2.2.6` (tag object `3333c550591501998b89d6029a567ac06f8d0f4c`, peeled commit `a7a9169c0cffbd2c007e6c899fef68396f240f60`) shows the causal order in `AbstractIoBuffer.getObject(ClassLoader)`: for descriptor type 1, `readClassDescriptor()` reads attacker-controlled `className` and calls `Class.forName(className, true, classLoader)` before any `acceptMatchers` decision. `initialize=true` permits `<clinit>` execution. Only later does `resolveClass()` test `acceptMatchers`, and its `clazz == null` branch calls `Class.forName(name, false, classLoader)` without checking the allowlist at all ([official 2.2.6 tag](https://github.com/apache/mina/tree/2.2.6); [affected source](https://github.com/apache/mina/blob/2.2.6/mina-core/src/main/java/org/apache/mina/core/buffer/AbstractIoBuffer.java)).

## Atomic BIC and immediate parent

The primary's proposed BIC, [`691a9df5a0aff0dddeedc5181f6e5832ee90dcea`](https://github.com/apache/mina/commit/691a9df5a0aff0dddeedc5181f6e5832ee90dcea), has immediate parent [`23e6ee17bae46bb8e7a76dd7aeb508ec89e76a25`](https://github.com/apache/mina/commit/23e6ee17bae46bb8e7a76dd7aeb508ec89e76a25). The parent already performs the vulnerable `Class.forName(className, true, classLoader)` and returns classes without an allowlist. The child merely adds `acceptMatchers` and a check later in `resolveClass()`. Thus the required parent-absence test fails; the primary even records `introducer_parent_absent: false`.

This is also disproved by release chronology. The CNA range starts at 2.1.0 and 2.2.0, while `691a9df5a0aff0dddeedc5181f6e5832ee90dcea` first appears in 2.2.4, and the parallel 2.1.X mitigation [`cdb59eb6131696a440870ab89ad0e20804eb5ca7`](https://github.com/apache/mina/commit/cdb59eb6131696a440870ab89ad0e20804eb5ca7), parent `88cb55397c414c6d09ce2d085ce912ab4bf45bf3`, first appears in 2.1.10. Neither can explain affected releases 2.2.0-2.2.3 or 2.1.0-2.1.9 ([Apache CNA CVE record](https://github.com/CVEProject/cvelistV5/blob/main/cves/2026/42xxx/CVE-2026-42778.json); [2.2.4 tag](https://github.com/apache/mina/tree/2.2.4); [2.1.10 tag](https://github.com/apache/mina/tree/2.1.10)).

Following the surviving sink backwards reaches [`f562722a84fb25ad233eb87f1e28e17ee0a8bd69`](https://github.com/apache/mina/commit/f562722a84fb25ad233eb87f1e28e17ee0a8bd69), parent `5a0b1f78b0507353aafdee7e3d367f5dabd88441`. It adds `ByteBuffer.getObject()` with the same `ObjectInputStream` and `Class.forName(className, true, classLoader)` behavior; its parent lacks that path. But its message is "temp move of all mina subprojects", its diff adds 262 paths, and its `git-svn-id` identifies an SVN tree move. It is an import/move aggregate, not the smallest writer permitted by the protocol. The vulnerable code is present by official tag 0.9.1 (tag object `74adef6b25eabbe5f254ec89905a06c72f23ea47`, peeled commit `3a7f59b1a3197e4b38dd09c38db104c710b75f5a`), but this Git history does not expose the pre-move atomic source writer ([official 0.9.1 tag](https://github.com/apache/mina/tree/0.9.1)). Atomic BIC and valid immediate-parent absence therefore remain unresolved.

## Squash or member decomposition

`691a9df5a0aff0dddeedc5181f6e5832ee90dcea` and `cdb59eb6131696a440870ab89ad0e20804eb5ca7` are ordinary single-parent commits, not squash or merge objects, but they are partial-mitigation commits rather than BICs. `f562722a84fb25ad233eb87f1e28e17ee0a8bd69` is likewise single-parent at the Git-object level, yet its 262-path SVN migration aggregate requires reconstruction of the original member revision; treating that aggregate as an atomic writer would violate the protocol ([691a9df5 object](https://github.com/apache/mina/commit/691a9df5a0aff0dddeedc5181f6e5832ee90dcea); [cdb59eb6 object](https://github.com/apache/mina/commit/cdb59eb6131696a440870ab89ad0e20804eb5ca7); [f562722a object](https://github.com/apache/mina/commit/f562722a84fb25ad233eb87f1e28e17ee0a8bd69)).

## Direct fix or unpatched state

The 2.1.X direct fix is [`ba8c355d82a010d677455df43b49725d21dbd07a`](https://github.com/apache/mina/commit/ba8c355d82a010d677455df43b49725d21dbd07a), parent `bfd80a05a69b6618947e0c6d74b598f663cdb288`. The 2.2.X direct fix is [`cca24d646c898adf7e01a765ebf6d677cc02b696`](https://github.com/apache/mina/commit/cca24d646c898adf7e01a765ebf6d677cc02b696), parent `b967f0b924d7516c4496832195e046b2a36d0847`. Both patches insert `acceptMatchers.stream().anyMatch(...)` before the type-1 `Class.forName(...)`, apply the same gate at the start of `resolveClass()`, and then resolve the class. Their parents retain the late/unconditional resolution path. The fixes' containment in 2.1.12 and 2.2.7, and absence from 2.1.11 and 2.2.6, matches the Apache CNA boundary.

## BIC-only AI attribution

No BIC-only attribution is possible because the BIC is unresolved. The object for `691a9df5a0aff0dddeedc5181f6e5832ee90dcea` names human Apache author and committer `emmanuel lecharny <elecharny@apache.org>` and has no AI/bot/generator/co-author trailer, but that object is only an incomplete mitigation. `f562722a84fb25ad233eb87f1e28e17ee0a8bd69` names `Alex Karasulu <akarasulu@apache.org>` and has no AI marker, but it is an excluded migration aggregate. Signals on either non-BIC object cannot establish `NOT_AI` ([691a9df5 object](https://github.com/apache/mina/commit/691a9df5a0aff0dddeedc5181f6e5832ee90dcea); [f562722a object](https://github.com/apache/mina/commit/f562722a84fb25ad233eb87f1e28e17ee0a8bd69)).

## Corrections

- Replace `introducer_sha: 691a9df5a0aff0dddeedc5181f6e5832ee90dcea` with `null`.
- Replace `introducer_parent: 23e6ee17bae46bb8e7a76dd7aeb508ec89e76a25` with `null` because that pair is not a valid BIC/parent pair.
- Replace `introducer_parent_absent: false` with `null`; the actual BIC parent has not been identified.
- Replace `ai_marker` with `null`; the cited human/no-trailer signal is on a mitigation, not on the BIC.
- Replace primary verdict `NOT_AI` with `EVIDENCE_GAP`.
- Retain direct fixes `ba8c355d82a010d677455df43b49725d21dbd07a` and `cca24d646c898adf7e01a765ebf6d677cc02b696`, with their branch-specific fixed-release membership.

## Remaining gap

Recover the pre-move Apache SVN history behind `f562722a84fb25ad233eb87f1e28e17ee0a8bd69`, identify the smallest revision that first wrote the vulnerable `getObject()`/`ObjectInputStream` class-resolution path, verify absence in that revision's immediate parent, and then inspect AI/bot/generator signals on that exact atomic object. Until those gates close, the verdict remains `EVIDENCE_GAP`.
