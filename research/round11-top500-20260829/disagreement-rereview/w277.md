# w277 re-research

## Decision

**AGREE** with the disagreement memo. Recommended primary verdict: **`NOT_AI`**. Recommended review verdict: **`CORRECTION_REQUIRED`**, limited to `introducer_parent_absent=true` and the historical path corrections below; the independent review's proposed `EVIDENCE_GAP` is not warranted.

The vulnerability, atomic BIC, immediate-parent absence, release membership, and unpatched state all close. The BIC object names the same non-bot account as author and committer, and the repository PR records that account adding the exact BIC as one of four public member commits. There is no AI, bot, generator, co-author, or signature signal on the BIC. Missing trailers alone would not prove human authorship, but that is not the whole evidence here.

## Vulnerability mechanism

CVE-2026-72600 is `PUBLISHED`, not rejected or withdrawn. Its CNA record describes CWE-284: an unauthenticated attacker can enumerate MongoDB ObjectIds and download invoice PDFs containing customer PII through `/download`; the CNA marks versions `0` through `4.1.0` affected. The GitHub advisory is likewise published and unwithdrawn, with patched versions unknown ([CVE record](https://cveawg.mitre.org/api/cve/CVE-2026-72600), [GHSA-93xg-c6hj-rp82](https://github.com/advisories/GHSA-93xg-c6hj-rp82)).

Replaying the route at BIC `e968bc95b8a1098d25d47d62615c4dd15e721941` gives the complete source-to-sink chain:

1. historical `app.js` mounts `coreDownloadRouter` at `/download` without `isValidAdminToken`, while the `/api` routers are mounted behind that middleware;
2. historical `routes/coreRoutes/coreDownloadRouter.js` accepts attacker-controlled `directory` and `id` and invokes `downloadPdf`;
3. the BIC-created historical `handlers/downloadHandler/downloadPdf.js` turns `directory` into a Mongoose model name, performs `Model.findById(ObjectId(id))`, calls `generatePdf` on the record, and returns the generated file with `res.download`.

There is no authentication or record-ownership check before the database lookup and PDF response. This is the same mechanism later reported in repository issue #1428 ([BIC commit and exact added sink](https://github.com/idurar/idurar-erp-crm/commit/e968bc95b8a1098d25d47d62615c4dd15e721941), [issue #1428](https://github.com/idurar/idurar-erp-crm/issues/1428)).

## Atomic BIC and immediate parent

The atomic BIC is `e968bc95b8a1098d25d47d62615c4dd15e721941` (`feat: create downloadPdf`), whose sole immediate parent is `4d74cb369fd8ab6ee998e35f92e54bcb7af01d13`. The BIC adds one new 56-line file, historical `handlers/downloadHandler/downloadPdf.js`, containing the first database lookup, PDF generation, and download response for this mechanism ([BIC object](https://github.com/idurar/idurar-erp-crm/commit/e968bc95b8a1098d25d47d62615c4dd15e721941), [parent object](https://github.com/idurar/idurar-erp-crm/commit/4d74cb369fd8ab6ee998e35f92e54bcb7af01d13)).

The immediate parent tree has no `handlers/downloadHandler/downloadPdf.js`. It does contain historical `routes/coreRoutes/coreDownloadRouter.js`, which already `require()`s that missing module and routes attacker-controlled IDs to it, and historical `app.js`, which already mounts `/download` without authentication. Thus the parent cannot execute the database-to-generated-PDF sink; the vulnerable mechanism is absent immediately before the BIC. The correct field is **`introducer_parent_absent=true`**.

Earlier commit `f22dc173e4e5e89364c20b9b2289f078f1eafc8a` created an unauthenticated `/download` route that only built a local `download/<directory>/<filename>` path and called `res.download`. It did not query MongoDB or generate a PDF from an enumerated object, so it is not the BIC for CVE-2026-72600's database-to-PDF mechanism ([earlier static-download commit](https://github.com/idurar/idurar-erp-crm/commit/f22dc173e4e5e89364c20b9b2289f078f1eafc8a)).

## Affected and fixed releases

The BIC is not an ancestor of tag `2.0.0` at `7ee1517f5867db7365c26c515377e91e8c3ecd36`, but it is an ancestor of `2.1.0` at `05116ac35d7fbf0be2e729cfcda6701b705cf631`. Local tag containment then includes the 3.x series and every available 4.x tag through `4.1.1`. In particular, both `4.1.0` at `012f39a43bdb899c9337fe76797f25357d473ff4` and `4.1.1` at `82ff5d1bcb8aa5a3feda5e7f94d71ba00d3a1a50` contain the BIC ([2.0.0 tag](https://github.com/idurar/idurar-erp-crm/tree/2.0.0), [2.1.0 tag](https://github.com/idurar/idurar-erp-crm/tree/2.1.0), [4.1.0 tag](https://github.com/idurar/idurar-erp-crm/tree/4.1.0), [4.1.1 tag](https://github.com/idurar/idurar-erp-crm/tree/4.1.1)).

The `4.1.0` and `4.1.1` trees both mount `/download` without `adminAuth.isValidAuthToken`. Thus repository evidence shows `4.1.1` is also affected even though the current CNA range stops at `4.1.0`. No fixed release exists in the repository tags.

## Direct fix or unpatched state

Commit `2b7eda9d51a1071ae15427290c22f993b7865e61` temporarily mounted `isValidAdminToken` on `/download`, but commit `050af4c7a5e07d9db07cfc3ed4fdcbe5f3ca86f6` removed that middleware two days later. No tag contains the former without the latter, so the short-lived mitigation never defines a fixed release ([temporary mitigation](https://github.com/idurar/idurar-erp-crm/commit/2b7eda9d51a1071ae15427290c22f993b7865e61), [mitigation removal](https://github.com/idurar/idurar-erp-crm/commit/050af4c7a5e07d9db07cfc3ed4fdcbe5f3ca86f6)).

As rechecked against the live remote refs, `master` remains `e935dec13cf8b6082a7e7fc4736669e5151a80a3` and `dev` remains `c36e1c1554898ec7709452dca424d768c7e91814`; both trees still mount `/download` without the token middleware. Issue #1428 is open. PR #1487 is also open, and its unmerged head `ebac0684d87db1c179f5be706c75c8d656d5e00b` adds the token gate and authenticated Axios download path. It is a concrete proposed fix, not a landed direct fix ([master object](https://github.com/idurar/idurar-erp-crm/commit/e935dec13cf8b6082a7e7fc4736669e5151a80a3), [dev object](https://github.com/idurar/idurar-erp-crm/commit/c36e1c1554898ec7709452dca424d768c7e91814), [PR #1487](https://github.com/idurar/idurar-erp-crm/pull/1487), [proposed fix object](https://github.com/idurar/idurar-erp-crm/commit/ebac0684d87db1c179f5be706c75c8d656d5e00b)).

The case is therefore verified **unpatched**, with no direct landed fix SHA and no fixed release.
