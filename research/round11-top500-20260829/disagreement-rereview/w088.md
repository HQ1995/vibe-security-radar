## Vulnerability mechanism

This is a real CWE-89 vulnerability, not a withdrawn or rejected advisory. The CVE record is `PUBLISHED` and describes authenticated glossary create and update endpoints before 4.1.7; the repository security advisory is published, has `withdrawn_at: null`, identifies affected versions `<= 4.1.6`, and names 4.1.7 as patched. [CVE-2026-76205 record](https://cveawg.mitre.org/api/cve/CVE-2026-76205) [vendor GHSA-79h3-6hxj-g98h](https://github.com/thorsten/phpMyFAQ/security/advisories/GHSA-79h3-6hxj-g98h)

At tag `4.1.6` (commit `58c1d7f2fa36f7074664fc6d862afee0ca8bcc89`), both `GlossaryRepository::create()` and `update()` first call `$db->escape($item)`, then apply `substr(..., 254)` to that escaped value, and finally interpolate it into a quoted SQL literal. The API controller passes JSON `item` and `definition` directly after permission and CSRF checks. [4.1.6 vulnerable repository](https://github.com/thorsten/phpMyFAQ/blob/4.1.6/phpmyfaq/src/phpMyFAQ/Glossary/GlossaryRepository.php#L93-L134) [4.1.6 controller](https://github.com/thorsten/phpMyFAQ/blob/4.1.6/phpmyfaq/src/phpMyFAQ/Controller/Administration/Api/GlossaryController.php#L85-L136)

I replayed the advisory's decisive byte transition under node-1 binding: `253 * "A" + "'"` becomes 255 bytes after quote escaping; slicing it to 254 bytes leaves `... 41 5c`, i.e. an `A` and a dangling backslash with the escaped quote removed. Substitution into the create template produced `VALUES ('...A\', ', (SELECT SLEEP(3)))-- ')`. Thus the next SQL quote is consumed by the dangling backslash and attacker-controlled `definition` enters SQL syntax. This is the exact mechanism described by the vendor advisory and exercised by the direct fix's regression tests. [vendor mechanism and reproducer](https://api.github.com/repos/thorsten/phpMyFAQ/security-advisories/GHSA-79h3-6hxj-g98h) [fix with regression tests](https://github.com/thorsten/phpMyFAQ/commit/bb3f06bd27c1291d0d424d5365e465b2b4908b01)

## Atomic BIC and immediate parent

There are two route-specific atomic BICs:

1. **Update:** `8b14f8c1f097480d2013a0f78fb198e008d9bf5a`, immediate parent `0db96193a3529ffc3801b94520f8d924c09bbd6c`. The parent already escapes update's `$item` but interpolates it without truncation. The BIC changes that expression to `Strings::htmlspecialchars(substr($item, 0, 254))`, thereby first creating escape-then-truncate on update. The same commit adds truncation to create, but create does not escape `$item` there, so that edit does not yet create this vulnerability on the create route. [BIC diff](https://github.com/thorsten/phpMyFAQ/commit/8b14f8c1f097480d2013a0f78fb198e008d9bf5a) [immediate parent tree](https://github.com/thorsten/phpMyFAQ/tree/0db96193a3529ffc3801b94520f8d924c09bbd6c)
2. **Create:** `781fdb661d9c66f4c2a2ba2b5cd39cefff257cc5`, immediate parent `cc4e183e6584fa4d748ee979810eb5e9d65f49d9`. The parent create path truncates raw `$item` without escaping it. The BIC creates `GlossaryRepository.php` and writes `$escapedItem = $db->escape($item)` followed by `substr($escapedItem, 0, 254)` into `create()`. This is a new causal ordering on create, not merely a relocation; update's corresponding code in the same commit is only a survival/refactor of the already-vulnerable update path. [create BIC diff](https://github.com/thorsten/phpMyFAQ/commit/781fdb661d9c66f4c2a2ba2b5cd39cefff257cc5) [immediate parent tree](https://github.com/thorsten/phpMyFAQ/tree/cc4e183e6584fa4d748ee979810eb5e9d65f49d9)

Both parents were present and replayed locally. Each lacks the route-specific vulnerable ordering introduced by its child. Therefore `introducer_parent_absent` is `true` for the primary `introducer_sha`, and parent absence is likewise established for the second path-specific BIC.

## Direct fix or unpatched state

`bb3f06bd27c1291d0d424d5365e465b2b4908b01` is the direct 4.1 release-line fix. In both create and update it replaces escape-then-truncate with `$db->escape($this->prepareItem($item))`; `prepareItem()` truncates/HTML-encodes before database escaping. The same object adds create/update regression cases using `253 * "A" + "'"`. It is absent from `4.1.6` and present in `4.1.7`.
