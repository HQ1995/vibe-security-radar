# w136 re-research

## Decision

**PARTIAL** with the disagreement memo.

- Recommended primary verdict: **`NOT_AI`**, but only after replacing the wrong 2024 BIC and parent fields with the reconstructed Apache SVN origin below.
- Recommended review verdict: **`CORRECTION_REQUIRED`**. The independent review correctly rejects `691a9df5a0aff0dddeedc5181f6e5832ee90dcea` as the BIC, but its `EVIDENCE_GAP` is no longer necessary: the first write and its immediate predecessor are recoverable from Apache's public pre-Git SVN history.

The disagreement memo is right that the primary's parent-absence gate failed and that `f562722a84fb25ad233eb87f1e28e17ee0a8bd69` is only an import/move. It is wrong only to the extent it accepts an unresolved-origin gap for w136: Apache SVN revision **r349422** is the smallest public revision that first writes the vulnerable `ByteBuffer.getObject(ClassLoader)` path, while r349421 has no `getObject`, `ObjectInputStream`, or `readObject` in that file ([r349422 file](https://svn.apache.org/repos/asf/!svn/rvr/349422/directory/network/trunk/src/java/org/apache/mina/common/ByteBuffer.java), [r349421 file](https://svn.apache.org/repos/asf/!svn/rvr/349421/directory/network/trunk/src/java/org/apache/mina/common/ByteBuffer.java)).

## Vulnerability mechanism

The Apache CNA record is `PUBLISHED` and defines a CWE-502 path in applications that call `IoBuffer.getObject()`: attacker-controlled framed bytes reach a custom `ObjectInputStream`; one class-resolution branch can reach `Class.forName()` without applying `acceptMatchers`, and `readObject()` can then instantiate a gadget chain. The official affected ranges are 2.1.0 through 2.1.11 and 2.2.0 through 2.2.6; the fixed releases are 2.1.12 and 2.2.7 ([CVE-2026-42779 CNA record](https://cveawg.mitre.org/api/cve/CVE-2026-42779), [GHSA-vf5j-865m-mq7c](https://github.com/advisories/GHSA-vf5j-865m-mq7c)).

The source-to-sink replay agrees with that scope. At the first affected tag commits, 2.1.0 `d595254cb8c254204d794457d42219321a6a2306` and 2.2.0 `079d4592943ff892504e11a331c4f6601b7a04ec`, `ObjectSerializationDecoder.doDecode()` passes the received `IoBuffer` to `in.getObject(classLoader)`. `AbstractIoBuffer.getObject()` builds `ObjectInputStream(asInputStream())`, resolves attacker-supplied class descriptors with `Class.forName`, and calls `in.readObject()` with no allowlist at all ([2.1.0 decoder](https://github.com/apache/mina/blob/d595254cb8c254204d794457d42219321a6a2306/mina-core/src/main/java/org/apache/mina/filter/codec/serialization/ObjectSerializationDecoder.java), [2.1.0 buffer](https://github.com/apache/mina/blob/d595254cb8c254204d794457d42219321a6a2306/mina-core/src/main/java/org/apache/mina/core/buffer/AbstractIoBuffer.java), [2.2.0 decoder](https://github.com/apache/mina/blob/079d4592943ff892504e11a331c4f6601b7a04ec/mina-core/src/main/java/org/apache/mina/filter/codec/serialization/ObjectSerializationDecoder.java), [2.2.0 buffer](https://github.com/apache/mina/blob/079d4592943ff892504e11a331c4f6601b7a04ec/mina-core/src/main/java/org/apache/mina/core/buffer/AbstractIoBuffer.java)).

The 2024 allowlist changes made the bypass narrower, not new: 2.1.11 `06b58eb0a75ed46b60c179a9c8434b9fbc0f0e09` and 2.2.6 `a7a9169c0cffbd2c007e6c899fef68396f240f60` call `setMatchers()` but check those matchers only when `desc.forClass()` is non-null; the null branch still executes unfiltered `Class.forName(name, false, classLoader)` ([2.1.11 buffer](https://github.com/apache/mina/blob/06b58eb0a75ed46b60c179a9c8434b9fbc0f0e09/mina-core/src/main/java/org/apache/mina/core/buffer/AbstractIoBuffer.java), [2.2.6 buffer](https://github.com/apache/mina/blob/a7a9169c0cffbd2c007e6c899fef68396f240f60/mina-core/src/main/java/org/apache/mina/core/buffer/AbstractIoBuffer.java)).

## Atomic BIC and immediate parent

The atomic BIC is Apache SVN **r349422** (2005-11-28, creator `trustin`, message headed `Resolved issues`, including `DIRMINA-126 ByteBuffer.get/putObject()`). Its modification of the already-existing `ByteBuffer.java` directly adds all of the vulnerable source-to-sink in one public revision:

1. the `getObject(ClassLoader)` API;
2. `ObjectInputStream(asInputStream())` over buffer-controlled bytes;
3. attacker-controlled descriptor-name loading by `Class.forName(className, true, classLoader)`; and
4. the terminal `in.readObject()`.

The exact immediate repository state, r349421, contains none of `getObject`, `ObjectInputStream`, or `readObject` in this file. This establishes parent absence rather than merely showing that a later filter was absent ([r349422 source](https://svn.apache.org/repos/asf/!svn/rvr/349422/directory/network/trunk/src/java/org/apache/mina/common/ByteBuffer.java), [r349421 parent source](https://svn.apache.org/repos/asf/!svn/rvr/349421/directory/network/trunk/src/java/org/apache/mina/common/ByteBuffer.java), [DIRMINA-126](https://issues.apache.org/jira/browse/DIRMINA-126)).

The assigned Git clone begins this lineage only at the later whole-tree move `f562722a84fb25ad233eb87f1e28e17ee0a8bd69` (parent `5a0b1f78b0507353aafdee7e3d367f5dabd88441`), whose commit message says it is a temporary move and whose parent lacks the MINA source. That Git object is not a BIC ([move commit](https://github.com/apache/mina/commit/f562722a84fb25ad233eb87f1e28e17ee0a8bd69)). Apache's SVN revision is the original public atomic commit; SVN revisions do not have a 40-hex Git object name, so no fabricated SHA is assigned to r349422.

## Squash or member decomposition

r349422 is one atomic SVN revision, not a merge, import, move, revert, or squash aggregate. It addresses three named issues and touches four files, but the vulnerable method is written directly in that smallest public revision; SVN exposes no finer member commits to decompose.

The later topology does not replace it:

- `a0bbdc9f052380799564e37fcfbdd7498412a814` adds a custom `resolveClass()` in 2007, but its immediate parent `b7801eb2585c00e83751be6ef04d427751f25254` already has the unfiltered `ObjectInputStream.readObject()` sink ([commit](https://github.com/apache/mina/commit/a0bbdc9f052380799564e37fcfbdd7498412a814)).
- `c1792331521ec1f50e9c71228a20ca4ab21029fa` introduces the `desc.forClass() == null` / non-null branch shape in 2014, but parent `c65e568a0ccfad4724f07976f2241e4697f381d2` already resolves classes without a filter and reads the object ([commit](https://github.com/apache/mina/commit/c1792331521ec1f50e9c71228a20ca4ab21029fa)).
- `691a9df5a0aff0dddeedc5181f6e5832ee90dcea` (2.2.X; parent `23e6ee17bae46bb8e7a76dd7aeb508ec89e76a25`) and `cdb59eb6131696a440870ab89ad0e20804eb5ca7` (2.1.X; parent `88cb55397c414c6d09ce2d085ce912ab4bf45bf3`) add an incomplete allowlist in 2024. Both parents remain vulnerable, and neither commit reaches the first affected release of its vendor-declared branch ([2.2.X commit](https://github.com/apache/mina/commit/691a9df5a0aff0dddeedc5181f6e5832ee90dcea), [2.1.X commit](https://github.com/apache/mina/commit/cdb59eb6131696a440870ab89ad0e20804eb5ca7)).

## Direct fix or unpatched state

Both affected lines have a direct fix:

- 2.1.X: `ba8c355d82a010d677455df43b49725d21dbd07a`, immediate parent `bfd80a05a69b6618947e0c6d74b598f663cdb288` ([commit](https://github.com/apache/mina/commit/ba8c355d82a010d677455df43b49725d21dbd07a)).
- 2.2.X: `cca24d646c898adf7e01a765ebf6d677cc02b696`, immediate parent `b967f0b924d7516c4496832195e046b2a36d0847` ([commit](https://github.com/apache/mina/commit/cca24d646c898adf7e01a765ebf6d677cc02b696)).

Each parent retains the null-class bypass. Each child moves the `acceptMatchers` decision ahead of `desc.forClass()` and every subsequent `Class.forName()` route, and also checks the type-1 descriptor before class loading. The fixes are single-parent member commits, not merge aggregates. Their later merge landings are `8cd26a303279606ae971bed846590e2af9afac18` for 2.1.X and `d108d0c86db11a901a986a456076699171c641f1` for 2.2.X ([2.1.X landing](https://github.com/apache/mina/commit/8cd26a303279606ae971bed846590e2af9afac18), [2.2.X landing](https://github.com/apache/mina/commit/d108d0c86db11a901a986a456076699171c641f1)).

Ancestry replay confirms `ba8c355d82a010d677455df43b49725d21dbd07a` is absent from 2.1.11 and present in 2.1.12, while `cca24d646c898adf7e01a765ebf6d677cc02b696` is absent from 2.2.6 and present in 2.2.7.

## BIC-only AI attribution

The judgment uses r349422 only. Its Apache SVN object records creator `trustin`, timestamp `2005-11-28T16:37:13.341752Z`, and a conventional issue-resolution message naming DIRMINA-126. The object contains no bot identity, AI/generator statement, or co-author marker. Apache's own committer index maps `trustin` to the named human **Trustin Lee** ([Apache committer index](https://people.apache.org/committer-index.html#trustin), [r349422 source snapshot](https://svn.apache.org/repos/asf/!svn/rvr/349422/directory/network/trunk/src/java/org/apache/mina/common/ByteBuffer.java)).

No later author, fix author, or AI-marked repository commit is used to reattribute the BIC. On the required BIC-only evidence, the writer is a named human and there is no AI/bot/generator marker; the supported verdict is `NOT_AI`.

## Corrections

- Replace `introducer_sha: 691a9df5a0aff0dddeedc5181f6e5832ee90dcea` with an explicit non-Git origin identifier: Apache SVN `r349422` (no 40-hex mapping exists in the assigned clone).
- Replace `introducer_parent: 23e6ee17bae46bb8e7a76dd7aeb508ec89e76a25` with Apache SVN `r349421`.
- Change `introducer_parent_absent` from `false` to `true` for the corrected BIC.
- Rewrite `flaw_origin`: r349422 first adds the unfiltered buffer-to-`ObjectInputStream.readObject()` path; `f562722a84fb25ad233eb87f1e28e17ee0a8bd69`, `a0bbdc9f052380799564e37fcfbdd7498412a814`, `c1792331521ec1f50e9c71228a20ca4ab21029fa`, `691a9df5a0aff0dddeedc5181f6e5832ee90dcea`, and `cdb59eb6131696a440870ab89ad0e20804eb5ca7` are later moves or mutations with vulnerable parents.
- Keep `verdict: NOT_AI`, but replace the old AI marker text with the r349422 creator/message evidence and the ASF `trustin` → Trustin Lee identity mapping.
- Keep the two direct-fix identities and affected/fixed release ranges.

## Remaining gap

No remaining causal, parent-absence, release, direct-fix, or BIC-attribution gap blocks the verdict. The archival limitation is representational: r349422 is an official Apache SVN revision and has no 40-hex Git mapping in the assigned `apache/mina` clone. That limitation must be encoded rather than inventing a SHA, but it does not erase the public atomic revision or its immediate predecessor.
