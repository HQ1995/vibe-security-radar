## Vulnerability mechanism

CVE-2026-48109 is published and the vendor advisory is not withdrawn. In affected MessagePack releases, deserialization with `Lz4Block` or `Lz4BlockArray` enabled accepts extension data, derives the destination length from the payload, and passes the remaining attacker-controlled compressed bytes to `LZ4Codec.Decode`. The fast decoder receives the destination length but no source length. Its token read, repeated `0xFF` literal-length reads, literal copy, two-byte offset read, and repeated match-length reads advance `src_p` without a `src_end` check. The later `length != input.Length` comparison occurs only after those native reads. A truncated literal run (`0xF0` followed by `0xFF` bytes) therefore reads past the compressed buffer, producing `AccessViolationException`/denial of service and potentially limited adjacent-memory disclosure. [Vendor advisory](https://github.com/MessagePack-CSharp/MessagePack-CSharp/security/advisories/GHSA-hv8m-jj95-wg3x) [CVE record](https://www.cve.org/CVERecord?id=CVE-2026-48109) [affected v3.1.6 decoder](https://github.com/MessagePack-CSharp/MessagePack-CSharp/blob/3a020c238ad98c9d737c7dee8b8c091097ebcec8/src/MessagePack/LZ4/LZ4Codec.Unsafe32.Dirty.cs) [direct fix and regression](https://github.com/MessagePack-CSharp/MessagePack-CSharp/commit/719e690abae8d4dba6b0c43088c8ded29cdc1ba2)

## Atomic BIC and immediate parent

The smallest surviving public first-write of the vulnerable decoding loop is Yann Collet's LZ4 commit `36104610053f34bbe033fad50263ce33cd4e9bcc` (the Git mapping of Google Code SVN revision 2). It adds `LZ4.c` with `LZ4_decode(char *source, char *dest, int isize)`. Although the outer loop knows `iend`, the newly written token-extension loops dereference `*ip++` without checking `iend`, the literal copy reads from `ip` without a source boundary check, the offset reads `*(U16*)ip`, and the match-length extension loop again dereferences without a bound. Those are the source semantics retained by the later destination-sized fast decoder and repaired in 2026. [atomic BIC](https://github.com/lz4/lz4/commit/36104610053f34bbe033fad50263ce33cd4e9bcc)

Its sole immediate parent is `409f2436903951a16feebc3e2cf3facf0fd50fbe`. That parent has no `LZ4.c`/decoder object; the file is added from `/dev/null` by `36104610053f34bbe033fad50263ce33cd4e9bcc`. Immediate-parent absence is therefore verified. [immediate parent](https://github.com/lz4/lz4/commit/409f2436903951a16feebc3e2cf3facf0fd50fbe) [BIC diff](https://github.com/lz4/lz4/commit/36104610053f34bbe033fad50263ce33cd4e9bcc#diff-40373cb6264d94f81d803a6321ffcb7b5612f842800b9954c88683cbbc1db34b)

## Direct fix or unpatched state

`719e690abae8d4dba6b0c43088c8ded29cdc1ba2` is the direct v3 fix. It changes both 32-bit and 64-bit decoder signatures to accept `src_len`, creates `src_end`, rejects end-of-source before token and extension-byte reads, checks literal lengths and the two-byte offset against the remaining source, and adds `Lz4BlockRejectsTruncatedLiteralRun`. Pull request 2275 carries this fix to `develop`. `3538bc1110ed8507b394348188c8075d3d8a3dbf` is the corresponding v2 backport. [v3 direct fix](https://github.com/MessagePack-CSharp/MessagePack-CSharp/commit/719e690abae8d4dba6b0c43088c8ded29cdc1ba2) [PR 2275](https://github.com/MessagePack-CSharp/MessagePack-CSharp/pull/2275) [v2 backport](https://github.com/MessagePack-CSharp/MessagePack-CSharp/commit/3538bc1110ed8507b394348188c8075d3d8a3dbf)
