## Vulnerability mechanism

At affected main-line trees, unauthenticated `GET /search.html?search=...` is read by `SearchController`, passed through `SearchService`, and reaches the database-selected search adapter. For the native PostgreSQL extension, `Search\Database\Pgsql::search()` embeds the escaped term in an `ILIKE ('%%%s%%')` pattern. The database driver's ordinary string escaping still handles quotes, so the demonstrated flaw is LIKE-wildcard injection and query-cost amplification, not quote-breaking SQL injection.

The broken invariant is exact: `SearchDatabase::escapeLikeWildcards()` converts `%` and `_` to `|%` and `|_`, but native `Pgsql.php` either has no explicit `ESCAPE` clause or, after the 4.1 merge, declares `ESCAPE '='`. PostgreSQL documents backslash as the default LIKE escape and says a different character must be selected with `ESCAPE`. Therefore the immediate-parent backslash escaper works with the native sink's omitted clause, while BIC `086c8ad58f91a8e34ea27fabd1ba9ca0b2487f42` makes `|` literal and leaves the attacker's `%`/`_` active. The later `ESCAPE '='` form remains mismatched. The PDO PostgreSQL sibling declares `ESCAPE '|'` and is not affected by this BIC mechanism. This source-to-sink behavior is also described by the [vendor advisory](https://github.com/thorsten/phpMyFAQ/security/advisories/GHSA-5hx6-c293-588h), the published [CVE-2026-76212 record](https://www.cve.org/CVERecord?id=CVE-2026-76212), and the [PostgreSQL LIKE documentation](https://www.postgresql.org/docs/current/functions-matching.html#FUNCTIONS-LIKE).

## Atomic BIC and immediate parent

The atomic landed BIC is [`086c8ad58f91a8e34ea27fabd1ba9ca0b2487f42`](https://github.com/thorsten/phpMyFAQ/commit/086c8ad58f91a8e34ea27fabd1ba9ca0b2487f42), a single-parent commit whose parent is [`9ad2874f52040a58ab8823c40fcc77f3ad46e7e7`](https://github.com/thorsten/phpMyFAQ/commit/9ad2874f52040a58ab8823c40fcc77f3ad46e7e7).

Mechanism-first pickaxe over `phpmyfaq/src/phpMyFAQ/Search/SearchDatabase.php` finds `086c8ad58f91a8e34ea27fabd1ba9ca0b2487f42` as the first writer of `str_replace(['|', '%', '_'], ['||', '|%', '|_'], $term)`. Its four-file patch changes the shared escaper, generic LIKE clauses, and PDO PostgreSQL clause from backslash to pipe, but the diff for native `phpmyfaq/src/phpMyFAQ/Search/Database/Pgsql.php` is empty.

The immediate parent `9ad2874f52040a58ab8823c40fcc77f3ad46e7e7` has native `Pgsql.php` calling the shared escaper from an `ILIKE` expression with no explicit `ESCAPE`, while the shared escaper prefixes `%`/`_` with backslash. That is consistent with PostgreSQL's documented default. The parent has neither the pipe escaper nor the resulting native mismatch. The vulnerable mechanism is therefore absent in the immediate parent and present after the BIC.

## Direct fix or unpatched state

[`17b7f5b0e181c6ced34887acc5f836eec7f6d0f8`](https://github.com/thorsten/phpMyFAQ/commit/17b7f5b0e181c6ced34887acc5f836eec7f6d0f8) is the direct fix. Its sole parent is [`f6899c3db6f8bdfb72612c1c0ec6a9cd282abf3a`](https://github.com/thorsten/phpMyFAQ/commit/f6899c3db6f8bdfb72612c1c0ec6a9cd282abf3a), whose native Pgsql clause still declares `ESCAPE '='` while the shared escaper uses `|`.

The fix defines `LIKE_ESCAPE_CHARACTER = '|'` once in `SearchDatabase`, makes native Pgsql, PDO Pgsql, generic LIKE construction, and `escapeLikeWildcards()` consume the same constant, and adds an adapter regression test asserting that `100%_|off` becomes `100|%|_||off` under `ESCAPE '|'`. This hunk directly repairs the mismatch and guards both PostgreSQL adapters against recurrence.
