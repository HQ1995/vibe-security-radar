# w008 re-research

## Decision

**AGREE** with the disagreement memo. Recommended primary verdict: `FALSE_POSITIVE`. Recommended review verdict: `CORRECTION_REQUIRED`.

The published advisory describes a real-looking AES-GCM-to-AES-CTR downgrade, but the claimed return path cannot execute. Every initialized `nonce` that can reach the fallback is exactly 12 bytes; `nonce[:16]` remains 12 bytes, while AES-CTR requires a 16-byte counter block. `cryptography==44.0.3` rejects construction before decryption, the fallback's own `except` catches that rejection, and the function raises `ValueError("Decryption failed: authentication error")`. The official [CVE record](https://cveawg.mitre.org/api/cve/CVE-2026-74901) remains `PUBLISHED`, and the [repository advisory](https://github.com/jahlives/openssl_encrypt/security/advisories/GHSA-w4j7-wfgw-r52w) remains published, but publication does not establish the contradicted execution path.

## Vulnerability mechanism

The advisory claims that an attacker can corrupt an AES-GCM ciphertext, trigger the exception at `cipher.decrypt(nonce, ciphertext, aad)`, then obtain unauthenticated plaintext from `Cipher(algorithms.AES(secure_key), modes.CTR(nonce[:16]))`. That description omits the nonce-length gate.

At the pre-removal tree, exact object `1fbf976096f419397dac5d89afe50a2d6309fbbd`, `PQCipher.decrypt()` has only these initialized nonce forms:

- `hashlib.sha256(encapsulated_key).digest()[:12]`;
- `remaining_data[:nonce_size]`, where `nonce_size = min(8, len(remaining_data))`, followed by zero-padding to 12 bytes;
- `remaining_data[:12]`.

The `TESTNONCE123` branch either returns embedded test plaintext before AEAD or leaves `nonce` unbound; the latter also fails before CTR can return. Across every stable tag containing the fallback, the nonce assignments above are unchanged. The repository pins `cryptography==44.0.3` in `requirements-prod.txt` at each such tag. The upstream [`cryptography` 44.0.3 CTR contract](https://cryptography.io/_/downloads/en/44.0.3/pdf/) requires the nonce length to equal the cipher block size; AES has a 16-byte block.

A node-1-bound replay using the repository's pinned `cryptography==44.0.3` constructed a valid 12-byte-nonce AES-GCM ciphertext, flipped one ciphertext bit, and ran the exact fallback construction. It produced, in order: `InvalidTag`, `ValueError: Invalid nonce size (12) for CTR.`, final `ValueError: Decryption failed: authentication error`, and `returned_plaintext False`. This matches the exception structure in exact pre-removal object [`1fbf976096f419397dac5d89afe50a2d6309fbbd`](https://github.com/jahlives/openssl_encrypt/commit/1fbf976096f419397dac5d89afe50a2d6309fbbd), where the inner fallback handler catches all `Exception` values before the final fail-closed raise.

Therefore ciphertext modification cannot traverse the advisory's alleged unauthenticated return. The syntactic CTR block is dead fail-closed code, not an authentication bypass.

## Corrections

- Change primary `verdict` from `AI_ROOT_CAUSE` to `FALSE_POSITIVE`.
- Replace the claimed bug semantics with: the apparent AES-CTR fallback is unreachable as a plaintext-returning path because all initialized nonces reaching it are 12 bytes, AES-CTR construction requires 16 bytes, the construction error is caught, and decryption fails closed.
- Set `introducer_sha`, `introducer_parent`, `fix_sha`, `direct_fix_sha`, and `ai_marker` to `null`.
- Keep `introducer_parent_absent: false`, `squash_decomposed: false`, and `decomposed_shas: []`.
- Preserve `5e3104481d9842d3d6989332ae32bee4b010d2db`, `295bf5f3df60ce08d2d8aed26d4fa0bc03592850`, and `65134868c092f1c3f0b75751413acc94031d0535` only as first-write/parent/dead-code-removal history, not causal vulnerability fields.
