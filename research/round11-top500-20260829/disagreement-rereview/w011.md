# w011 re-research

## Decision

**AGREE** with the disagreement memo. Recommended primary verdict: `AI_ROOT_CAUSE`. Recommended review verdict: `CORRECTION_REQUIRED`, limited to impact and release wording; the causal TP is stable.

The vulnerability is real, the smallest surviving public BIC is AI-marked, and the direct fix confirms the defective mechanism. The corrections do not destabilize that chain: the Bearer bypass enables unauthenticated upload, but search was already public and revocation independently requires proof of ownership. The official CNA record remains `PUBLISHED`, while the repository advisory is published and not withdrawn ([CVE-2026-74894](https://cveawg.mitre.org/api/cve/CVE-2026-74894), [GHSA-4g2c-wpgj-49w8](https://api.github.com/repos/jahlives/openssl_encrypt/security-advisories/GHSA-4g2c-wpgj-49w8)).

## Vulnerability mechanism

In `server/key-server/app/api/v1/keys.py`, `verify_api_token` accepts any header beginning with `Bearer ` whose remainder is non-empty. It checks no signature, shared secret, issued-token store, or other credential and then returns `True`. `upload_key` installs that function as a FastAPI dependency, so `Authorization: Bearer x` reaches the upload handler. The handler still verifies the submitted bundle's self-signature and fingerprint, meaning the demonstrated effect is unauthenticated upload of an otherwise-valid attacker-controlled self-signed public-key bundle, not acceptance of an arbitrary malformed bundle ([BIC source: authentication and upload](https://github.com/jahlives/openssl_encrypt/blob/fafdfeed1b279cfe61e86cd8adc132b206eef8d4/server/key-server/app/api/v1/keys.py#L48-L192), [bundle verification](https://github.com/jahlives/openssl_encrypt/blob/fafdfeed1b279cfe61e86cd8adc132b206eef8d4/server/key-server/app/services/verification.py#L47-L163)). This is a real CWE-287 authentication bypass.

The broader advisory impact is not borne out by the route logic. `GET /api/v1/keys/search` deliberately has no authentication dependency, so search/enumeration does not result from bypassing `verify_api_token` ([search route](https://github.com/jahlives/openssl_encrypt/blob/fafdfeed1b279cfe61e86cd8adc132b206eef8d4/server/key-server/app/api/v1/keys.py#L195-L252)). The revoke route does use the defective Bearer dependency, but before changing state it verifies a signature over the target fingerprint against the signing public key stored in that target's bundle. Therefore an arbitrary Bearer value alone cannot revoke another party's key ([revoke route](https://github.com/jahlives/openssl_encrypt/blob/fafdfeed1b279cfe61e86cd8adc132b206eef8d4/server/key-server/app/api/v1/keys.py#L255-L334), [revocation verifier](https://github.com/jahlives/openssl_encrypt/blob/fafdfeed1b279cfe61e86cd8adc132b206eef8d4/server/key-server/app/services/verification.py#L187-L245)).

## Direct fix or unpatched state

[`1d519a1eb1a29936d087fc7d98dc84a4718098c9`](https://github.com/jahlives/openssl_encrypt/commit/1d519a1eb1a29936d087fc7d98dc84a4718098c9) is the direct fix. Its only parent is [`6090a8e329230b5c4b941dcedee4cc4b78bb35a7`](https://github.com/jahlives/openssl_encrypt/commit/6090a8e329230b5c4b941dcedee4cc4b78bb35a7), where the BIC-authored stub still accepts every non-empty Bearer value. The fix replaces that stub with HMAC-SHA256 signature verification using `hmac.compare_digest`, plus expiration and issuer checks, and requires a minimum-length `API_TOKEN_SECRET` outside debug mode. Its commit message directly says it resolves `GHSA-4g2c-wpgj-49w8` ([fix diff](https://github.com/jahlives/openssl_encrypt/commit/1d519a1eb1a29936d087fc7d98dc84a4718098c9)). This source-to-sink repair confirms that missing credential validation—not search visibility or missing revocation ownership—is the defect fixed for this advisory.

## Corrections

1. Replace “search/enumerate all keys via the bypass” with “search was intentionally public and did not depend on authentication.”
2. Replace “revoke arbitrary keys with any Bearer token” with “the Bearer check was bypassable, but revocation independently required a valid signature from the target bundle's private signing key.”
3. Replace “upload arbitrary public keys” with “unauthenticated upload of an otherwise-valid self-signed attacker-controlled bundle”; bundle signature, algorithm, and fingerprint validation still ran.
4. Describe `<1.4.0` as the CNA/vendor metadata range. The public Git evidence shows a vulnerable development interval, no tag containing BIC without fix, `v1.3.6` without the subsystem, and fixed `v1.4.0`.
5. Keep `introducer_sha=fafdfeed1b279cfe61e86cd8adc132b206eef8d4`, `introducer_parent=4c7ae852c784c9986d087c5956a77fa563a05a35`, `direct_fix_sha=1d519a1eb1a29936d087fc7d98dc84a4718098c9`, and verdict `AI_ROOT_CAUSE` unchanged.
