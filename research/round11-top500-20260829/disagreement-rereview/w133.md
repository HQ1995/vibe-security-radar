# w133 re-research

## Decision

**DISAGREE** with the disagreement memo's instruction to accept an atomic-BIC/mechanism gap. Recommended primary verdict: **NOT_AI**. Recommended review verdict: **CORRECTION_REQUIRED**.

The review merged two different mechanisms. The immediate parent is vulnerable to the older, unbounded-deserialization issue recorded as CVE-2024-52046, but it cannot contain CVE-2026-41635's specifically named “null-clazz branch skips acceptMatchers filter” mechanism because `acceptMatchers` does not yet exist there. The smallest public object that creates that incomplete-control pairing is `691a9df5a0aff0dddeedc5181f6e5832ee90dcea`; its exact object has a named human author/committer and no AI marker. The Apache CNA record names the null-clazz/`acceptMatchers` bypass, while the prior Apache CNA record separately names the pre-filter unbounded deserialization issue ([CVE-2026-41635 CNA record](https://raw.githubusercontent.com/CVEProject/cvelistV5/main/cves/2026/41xxx/CVE-2026-41635.json), [CVE-2024-52046 vendor advisory](https://lists.apache.org/thread/4wxktgjpggdbto15d515wdctohb0qmv8), [`691a9df5a0aff0dddeedc5181f6e5832ee90dcea`](https://github.com/apache/mina/commit/691a9df5a0aff0dddeedc5181f6e5832ee90dcea)).

## Vulnerability mechanism

`IoBuffer.getObject()` builds an `ObjectInputStream` over attacker-supplied serialized bytes and ends at `readObject()`. For a type-0 descriptor, `readClassDescriptor()` delegates to the superclass; `resolveClass()` then receives an `ObjectStreamClass`. Commit `691a9df5a0aff0dddeedc5181f6e5832ee90dcea` introduced `acceptMatchers`, but consulted it only in the `desc.forClass() != null` arm. When `desc.forClass() == null`, execution instead reached `Class.forName(name, false, classLoader)` without consulting the allowlist. Thus a class in the null-clazz/static-or-primitive route bypassed the newly installed control before `readObject()` completed ([Apache advisory](https://lists.apache.org/thread/1l91w1mqsb3lwfd504fs045ylxntt2tm), [CVE record](https://raw.githubusercontent.com/CVEProject/cvelistV5/main/cves/2026/41xxx/CVE-2026-41635.json), [`691a9df5a0aff0dddeedc5181f6e5832ee90dcea` diff](https://github.com/apache/mina/commit/691a9df5a0aff0dddeedc5181f6e5832ee90dcea)).

This is narrower than “native deserialization exists.” Apache had already assigned CVE-2024-52046 to that older condition: MINA used native deserialization without necessary checks, reachable when applications call `IoBuffer.getObject()` (including through `ObjectSerializationCodecFactory`). The old source-to-sink is real, but it is not the first-write question for the later allowlist-bypass CVE ([CVE-2024-52046 CNA record](https://raw.githubusercontent.com/CVEProject/cvelistV5/main/cves/2024/52xxx/CVE-2024-52046.json), [Apache's archived announcement](https://www.openwall.com/lists/oss-security/2024/12/25/1)).

## Atomic BIC and immediate parent

The canonical BIC is `691a9df5a0aff0dddeedc5181f6e5832ee90dcea` on `2.2.X`. It simultaneously adds the allowlist API/storage and changes `resolveClass()` so only the non-null arm checks that allowlist. Its sole immediate parent is `23e6ee17bae46bb8e7a76dd7aeb508ec89e76a25`. The parent has `getObject()`, `readObject()`, and unfiltered `Class.forName()` calls, but `git grep acceptMatchers 23e6ee17bae46bb8e7a76dd7aeb508ec89e76a25 -- mina-core/src/main/java/org/apache/mina/core/buffer/AbstractIoBuffer.java` is empty. Therefore the parent has CVE-2024-52046's mechanism, while CVE-2026-41635's filter-bypass pairing is absent ([BIC](https://github.com/apache/mina/commit/691a9df5a0aff0dddeedc5181f6e5832ee90dcea), [immediate parent](https://github.com/apache/mina/commit/23e6ee17bae46bb8e7a76dd7aeb508ec89e76a25)).

Earlier objects confirm, rather than displace, that boundary. `a0bbdc9f052380799564e37fcfbdd7498412a814` added the custom-classloader `resolveClass()` in 2007, and `c1792331521ec1f50e9c71228a20ca4ab21029fa` introduced the later `desc.forClass()` null/non-null split in 2014; neither object contains an allowlist that one arm can bypass ([`a0bbdc9f052380799564e37fcfbdd7498412a814`](https://github.com/apache/mina/commit/a0bbdc9f052380799564e37fcfbdd7498412a814), [`c1792331521ec1f50e9c71228a20ca4ab21029fa`](https://github.com/apache/mina/commit/c1792331521ec1f50e9c71228a20ca4ab21029fa)).

The same incomplete control was then written independently on the maintenance branches by `834396355766e0c8f6bbf0493d4588b3fa9d347d` (`2.0.X`, parent `e1eaa679167cd099305ec49fb6f8ca095836b852`) and `cdb59eb6131696a440870ab89ad0e20804eb5ca7` (`2.1.X`, parent `88cb55397c414c6d09ce2d085ce912ab4bf45bf3`). They are branch ports of the same mechanism, not earlier or finer members of the canonical BIC ([`834396355766e0c8f6bbf0493d4588b3fa9d347d`](https://github.com/apache/mina/commit/834396355766e0c8f6bbf0493d4588b3fa9d347d), [`cdb59eb6131696a440870ab89ad0e20804eb5ca7`](https://github.com/apache/mina/commit/cdb59eb6131696a440870ab89ad0e20804eb5ca7)).

## Squash or member decomposition

`691a9df5a0aff0dddeedc5181f6e5832ee90dcea` is a single-parent public commit, not a merge. It is large (13 files, 1,308 additions), but size alone is not evidence of a squash. The official GitHub commit-to-pulls endpoint returns an empty array, and all-ref history of `mina-core/src/main/java/org/apache/mina/core/buffer/matcher/ClassNameMatcher.java` begins at this exact object; no finer public member object exists to decompose. Under the protocol, it is therefore the smallest surviving public object ([commit object](https://github.com/apache/mina/commit/691a9df5a0aff0dddeedc5181f6e5832ee90dcea), [associated-PR query](https://api.github.com/repos/apache/mina/commits/691a9df5a0aff0dddeedc5181f6e5832ee90dcea/pulls)).

The later maintenance-branch objects `834396355766e0c8f6bbf0493d4588b3fa9d347d` and `cdb59eb6131696a440870ab89ad0e20804eb5ca7` are whole, single-parent public ports. They do not decompose `691a9df5a0aff0dddeedc5181f6e5832ee90dcea`.

## Corrections

1. The independent review's atomic-BIC and parent-absence failures are incorrect for CVE-2026-41635: they prove the parent has CVE-2024-52046's old source-to-sink, not that it has a null-clazz bypass of `acceptMatchers`.
2. The primary's `introducer_parent_absent: false` should be **true for the named CVE-2026-41635 mechanism**. Textually, the old `Class.forName()` call is present in the parent; causally, the incomplete allowlist pairing is absent.
3. The primary verdict `NOT_AI`, canonical BIC `691a9df5a0aff0dddeedc5181f6e5832ee90dcea`, and direct-fix reconstruction are retained.
4. The CNA/vendor affected ranges conflate the old unrestricted-deserialization releases with the later incomplete-control bypass. The CNA/vendor fixed versions are also wrong for `2.1.X` and `2.2.X`: repository tags first contain the fixes in 2.1.12 and 2.2.7, not 2.1.11 and 2.2.6.

## Remaining gap

No BIC or BIC-object attribution gap remains. The remaining non-blocking upstream-record gap is that Apache/CVE.org still declare pre-allowlist releases affected by this allowlist-bypass CVE and still declare 2.1.11/2.2.6 fixed, while the official repository objects show otherwise. Apache/CVE.org should correct those release boundaries; this discrepancy does not make the public BIC identity ambiguous.
