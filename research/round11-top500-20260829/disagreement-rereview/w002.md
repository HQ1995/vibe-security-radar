## Vulnerability mechanism

The security boundary begins when the program accepts a plugin file, applies a source check, and executes it. In `8a5ed7e62417441ed98b39481ac1a47510c1a9ef`, `_validate_plugin_file()` searches for seven literal substrings (`import os.system`, `exec(`, `eval(`, `__import__`, `open(`, `subprocess`, and `ctypes`), then `load_plugin()` executes accepted source through `spec.loader.exec_module(module)` with ordinary Python builtins ([BIC commit](https://github.com/jahlives/openssl_encrypt/commit/8a5ed7e62417441ed98b39481ac1a47510c1a9ef)).

I replayed those exact literals from the BIC object against `__builtins__["__im" + "port__"]("pickle")`: the match set was empty, and normal Python execution reached the `pickle` module. This is the source-to-sink path: obfuscated dynamic import bypasses validation, then plugin module execution obtains a dangerous module.

The later, narrower mechanism named by the vendor advisory is real too. At `50bec5d3656d62b8dbbb0ce082fd67b8436677fd`, the actual AST analyzer rejects direct `import pickle`, but accepts the same obfuscated expression; the actual `PluginImportGuard._should_block_module("pickle")` returns false and `hide_dangerous_modules()` leaves `pickle` in `sys.modules`. The advisory likewise identifies the mismatch between `DANGEROUS_MODULES` and the runtime guard and lists `sys`, `shutil`, `multiprocessing`, `importlib`, and `pickle` as reachable after AST bypass ([vendor advisory](https://github.com/jahlives/openssl_encrypt/security/advisories/GHSA-9pgj-v69p-q586), [AST-introducing commit](https://github.com/jahlives/openssl_encrypt/commit/50bec5d3656d62b8dbbb0ce082fd67b8436677fd)).

Therefore the repository-supported vulnerable release range for the original plugin import/execution path starts at `>=1.3.0`, not version `0`. The PUBLISHED CNA record says `0..<1.4.0` affected and `1.4.0` unaffected; its upper boundary matches tag containment, but its lower boundary is overbroad ([CVE record API](https://cveawg.mitre.org/api/cve/CVE-2026-74886)). The exact two-list mismatch first exists only after `50bec5d3656d62b8dbbb0ce082fd67b8436677fd` and was fixed before the `v1.4.0` tag, so no inspected stable tag contains that narrower mismatch.

## Direct fix or unpatched state

`e0c999ea44429e8de00b4acb3ba570efdc733092`, parent `09e96e090417d34d2f533f6810d3cd4f77810101`, is the direct fix for the advisory's named list-desynchronization mechanism. It creates `BLOCKED_MODULES` and makes both the AST analyzer and runtime guard consume it ([fix commit](https://github.com/jahlives/openssl_encrypt/commit/e0c999ea44429e8de00b4acb3ba570efdc733092)). Replaying the fixed objects showed that the obfuscated expression still passes static AST analysis, but the runtime guard now returns true for `pickle` and removes it from `sys.modules`; that is direct closure of the named runtime-list gap.

The fix is not evidence of complete closure of every import sink. In `v1.4.0`, `PluginManager.load_plugin()` still performs validation and then calls `spec.loader.exec_module(module)` before any `PluginImportGuard` is installed ([v1.4.0 loader](https://github.com/jahlives/openssl_encrypt/blob/768df5cd1910e349509f07a27eeac6951e0003bf/openssl_encrypt/modules/plugin_system/plugin_manager.py#L150-L217)). Because the same obfuscated import passes the fixed AST analyzer, `e0c999ea44429e8de00b4acb3ba570efdc733092` should be retained as `fix_sha`/`direct_fix_sha` only for the advisory-scoped runtime mismatch, not cited as proof that the full untrusted-plugin import surface is patched.

## Remaining gap

The named list mismatch is closed, but full exploit closure is not established: the `v1.4.0` plugin loader still executes an AST-accepted module before installing the runtime import guard. A complete patched-state claim needs first-party evidence that this import-time sink is unreachable for attacker-controlled plugins or a direct guard/sandbox around module loading. This gap does not change the BIC-only `AI_ROOT_CAUSE` verdict.
