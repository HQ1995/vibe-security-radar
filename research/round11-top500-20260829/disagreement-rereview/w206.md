# w206 re-research

## Decision

**AGREE** with the disagreement memo. Recommended primary verdict: `NOT_AI`. Recommended review verdict: `CORRECTION_REQUIRED`.

The primary correctly rejected the advisory's literal unauthenticated/plain-webshell account, but it incorrectly promoted that correction to `FALSE_POSITIVE`. The same named upload route has a real, authenticated and configuration-dependent path-escape write when `erupt.keepUploadFileName=true`. Commit `1405b8b1fe76842514d915f360c731db14b80324` is the smallest surviving public BIC, and its object supports a human, non-AI attribution. The independent review's core correction is therefore right, with a release-boundary correction noted below.

## Vulnerability mechanism

At tag `1.12.19` (`ea793f7143eb474a02faab43c60306d4b2223d6e`), `POST /erupt-api/file/upload/{erupt}/{field}` is guarded by `@EruptRouter(... verifyType = ERUPT)`, the security interceptor requires a live token and matching menu, and `Erupts.powerLegal` requires add or edit power. Thus the CVE record's `PR:N` and an unauthenticated reading are wrong. The named `GoodsCategory.image` field was introduced in the first-party example repository by `9708c88d2543686ec1dd17e407db1418be0d8cf1` as `AttachmentType.Type.IMAGE`, so non-image input is rejected by `ImageIO.read`.

That does not close the route. With `keepUploadFileName=true`, `EruptFileService.createPath` appends `MultipartFile.getOriginalFilename()` after removing only `&`, `#`, `?`, and whitespace; it leaves `..` and path separators intact. `upload` then constructs `new File(eruptProp.getUploadPath() + path)` and calls `file.transferTo(dest)` without canonicalization or an upload-root check. Spring Framework 5.3.31, selected by erupt's Spring Boot 2.7.18 dependency, explicitly says `getOriginalFilename()` is client supplied, may contain path information or `..`, and must not be used blindly; its standard multipart parser carries the parsed `filename` into `StandardMultipartFile` without basename stripping.

I replayed both gates directly: a one-pixel GIF with an appended JSP text tail still produced a non-null `ImageIO.read`, and a filename `../../../../tmp/w206.jpg` normalized outside `/opt/erupt-attachment`; the later fix's `startsWith(uploadRoot)` check returned false for that target. This closes an authenticated, configuration-dependent arbitrary-path file write. It does not by itself prove code execution on every deployment, because execution additionally depends on a writable executable target and its runtime handler.

## Atomic BIC and immediate parent

`git log -S'file.getOriginalFilename()'` and `git log -S'file.transferTo'` on the upload implementation lead to single-parent commit `1405b8b1fe76842514d915f360c731db14b80324` (2019-01-17). Relative to immediate parent `539a56a29cb22f871bafce3ff64572a276d505ec`, it changes `EruptFileController` from an empty stub into `POST /upload/{erupt}/{field}`, derives the destination from `file.getOriginalFilename()`, creates `new File(uploadPath + File.separator + path)`, and reaches `file.transferTo(dest)`. The parent has no multipart source, upload route, path construction, or file-write sink. The BIC is an ancestor of the affected release commits inspected below.

Commit `8389cc152b593dca76898050517cb23706c14f58` (parent `808b1a3a78feba5c6b6320a01f9f0a21965493f1`) later made random naming the default through `keepUploadFileName=false`, but deliberately retained original-name construction behind the true branch. It reduced default exposure; it did not introduce the flaw and is not the BIC.

## Squash or member decomposition

`1405b8b1fe76842514d915f360c731db14b80324` has exactly one parent, `539a56a29cb22f871bafce3ff64572a276d505ec`, and is not a merge. Its own diff first writes the complete vulnerable source-to-sink chain. No finer public PR member or predecessor object exists in the allowed repository history, so it is the smallest surviving public writer under the protocol; no squash-member substitution is needed.

## Affected and fixed releases

The vulnerable true branch and unchecked `File`/`transferTo` sink are present in these inspected tags:

- `1.12.19` -> `ea793f7143eb474a02faab43c60306d4b2223d6e`
- `1.12.20` -> `922847d72a473ce5238ae68610a998a790f411bd`
- `1.12.21` -> `e814b8a19db50e692d8c70b32f96b5dd07ffea6d`
- `1.12.23` -> `480e17032f2d4fadb6c08a4c24591f84711eee30`

This matters because `1.12.23` was tagged on 2025-08-07, after CVE publication. GitHub Advisory Database still says affected `<= 1.12.19` and patched versions `None`; that metadata is incomplete for the path-escape mechanism.

The first repository tag containing direct fix `58ed8631700f82c2d079e969b4ecbc2279eb2fde` is `1.13.1`, commit `a2ffd1164e53d96811f3506fdc66515c4e5fb378` (2025-11-06), the merge commit for PR `#332`. This is a Git-containment boundary, not an official CVE-to-release statement from the vendor.

## Direct fix or unpatched state

Direct fix `58ed8631700f82c2d079e969b4ecbc2279eb2fde` (2025-10-14), relative to parent `dcd8080924ec65b987401f00212d2adf6c9a6636`, replaces `new File(uploadPath + path)` with `Paths.get(uploadPath).resolve(path.substring(1)).normalize()`, rejects a target that does not start with the upload root, and transfers only to the checked target. The same object applies an analogous containment check to downloads. That is an exact source-to-sink repair for the path escape, even though its message, "optimize code with qodana, up code security", does not mention CVE-2025-45855.

Tags `1.12.20`, `1.12.21`, and `1.12.23` retain the old unchecked sink. Tag `1.13.1` contains the normalized target and root-prefix rejection.

## BIC-only AI attribution

Only BIC `1405b8b1fe76842514d915f360c731db14b80324` was used for attribution. Its raw commit object records the same author and committer, `122339792@qq.com <Lyp19824135>`, at the same 2019 timestamp; it has no co-author trailer, bot identity, generator marker, AI marker, or signature payload. The BIC's own additions include an `ImageType.java` author comment naming `liyuepeng` and a demo upload path under `/Users/yuepeng/`, providing human-associated authorship signals on the object itself. These signals support `NOT_AI`.

The Qodana wording on the 2025 fix is fix-side evidence and was not used to attribute the 2019 defect writer.

## Corrections

1. Primary: replace `FALSE_POSITIVE` with `NOT_AI`; replace “nothing to patch” with the authenticated `keepUploadFileName=true` path-escape mechanism and direct fix above. Keep the primary's correction that the endpoint is authenticated and IMAGE-gated.
2. Independent review: extend the verified unpatched release set beyond `1.12.20` to `1.12.21` (`e814b8a19db50e692d8c70b32f96b5dd07ffea6d`) and `1.12.23` (`480e17032f2d4fadb6c08a4c24591f84711eee30`).
3. Claim boundary: call `58ed8631700f82c2d079e969b4ecbc2279eb2fde` the direct code fix for the demonstrated path escape, not an officially acknowledged CVE fix; neither the commit nor PR `#332` names the CVE.
4. Impact boundary: arbitrary-path file write is closed; universal RCE and the advisory's `PR:N` statement are not.

## Remaining gap

No vendor advisory, commit message, PR text, CNA update, or GHSA patched-version field explicitly maps CVE-2025-45855 to `58ed8631700f82c2d079e969b4ecbc2279eb2fde` or `1.13.1`. The supplied advisory reference has no end-to-end exploit, and this re-research did not stand up a deployed servlet container to prove JSP execution at a writable executable target. Those gaps limit the RCE and official-release claims; they do not reopen the demonstrated upload-root escape, atomic BIC, parent absence, direct containment fix, or BIC-only `NOT_AI` attribution.
