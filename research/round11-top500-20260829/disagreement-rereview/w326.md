## Vulnerability mechanism

`src/middleware.ts` applies `withMobileAuth` to `/api/mobile/:path*`. Its first branch returns `NextResponse.next()` when `Auth-Key` is merely present; it neither compares the value with a server-side secret nor verifies a JWT. On the JWT path the middleware overwrites request header `g` with verified claims, but on the `Auth-Key` path it forwards the caller's headers unchanged. `src/app/api/mobile/search/route.ts` then parses `g` and uses `user.id` to select purchased course/video titles and identifiers. Thus `Auth-Key: anything` plus a forged `g` reaches protected search data without authentication, matching the reporter's HTTP 200 PoC and the published CVE description. ([reporter evidence](https://gist.github.com/itsmohitnarayan/e456399f083130962bab6c710f208437), [current middleware](https://github.com/code100x/cms/blob/9f3c8f426cdaf22948f9f8e16e32f24fb7c9d059/src/middleware.ts), [current search route](https://github.com/code100x/cms/blob/9f3c8f426cdaf22948f9f8e16e32f24fb7c9d059/src/app/api/mobile/search/route.ts))

The CNA record is `PUBLISHED` and the GitHub advisory has `withdrawn_at: null`; this is not a withdrawn or rejected advisory. ([CVE record](https://cveawg.mitre.org/api/cve/CVE-2026-52021), [GitHub advisory API](https://api.github.com/advisories/GHSA-8qr5-q795-mv79))

## Atomic BIC and immediate parent

The atomic public BIC is `a60ba45f26cb15e51d5077b8f2e11c5cbd2c29d9`. Its diff moves mobile authentication into the active `src/middleware.ts`, adds `/api/mobile/:path*` to that middleware's matcher, and first writes the vulnerable presence-only branch:

```typescript
if (req.headers.get('Auth-Key')) {
  return NextResponse.next();
}
```

Its sole immediate parent is `cd900552043f414334dc9a03e14b40add8c84cd4`. In that parent, `src/withMobileAuth.ts` extracts an `Authorization` bearer token, validates the JWT, and rejects missing or invalid tokens; the parent tree has no presence-only `Auth-Key` branch. The parent already demonstrates the intended secret-comparison pattern in mobile signin: `Auth-Key` must equal `EXTERNAL_LOGIN_AUTH_SECRET`. ([BIC and diff](https://github.com/code100x/cms/commit/a60ba45f26cb15e51d5077b8f2e11c5cbd2c29d9), [immediate parent](https://github.com/code100x/cms/commit/cd900552043f414334dc9a03e14b40add8c84cd4))

At the BIC, search still uses a hard-coded user id, but the newly active bypass already permits an unauthenticated request to obtain protected search results for that identity. Therefore later identity-forgery work intensifies the impact but does not displace the first vulnerable commit.
