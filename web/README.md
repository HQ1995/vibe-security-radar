# Vibe Security Radar — Web Dashboard

Next.js static site that visualizes vulnerability data produced by [cve-analyzer](../cve-analyzer/).

## Stack

- **Next.js 16** (App Router, static export)
- **React 19** + **TailwindCSS 4**
- **Recharts** for charts (pie, bar)
- **Radix UI** primitives (dialog, tooltip, badge, etc.)

## Setup

```bash
npm install
```

## Data

The site reads one validated publication generation at build and revalidation
time:

| File | Contents | Generated by |
|------|----------|--------------|
| `data/index.json` | Manifest with generation timestamp, total, and ordered ids | `scripts/generate_web_data.py` |
| `data/cves/<ID>.json` | One vulnerability entry per file | `scripts/generate_web_data.py` |
| `data/stats.json` | Aggregate stats (by tool, severity, month) | `scripts/generate_web_data.py` |

`src/lib/data.ts` validates the manifest, checks its ids against the exact set
of files, verifies entry filename/id identity and generation totals, then
assembles the existing in-memory `CvesData` shape. A malformed, partial, or
mixed generation stops the build. Per-CVE files make data changes reviewable
as focused additions, removals, and field diffs.

The Python producer validates and stages every file before promoting the whole
`data/` directory. See [`scripts/web_data/README.md`](../scripts/web_data/README.md)
for the schema, publication, and interruption-safety contracts.

Production builds require `data/release-receipt.json`. The Web loader
recomputes the exact byte manifest for `index.json`, `stats.json`, and every
per-vulnerability file. The postbuild verifier then calls
`scripts/verify_formal_release.py` to recompute the Python canonical generation
and bundle, validate the schema-3 source cutoff, and cross-check the raw
manifest. Development keeps the receipt optional while retaining the raw
inventory and generation-consistency checks.

`npm run verify:formal-release` additionally requires the local schema-5 active
activation and complete archived evidence under
`.ai-slop/state/data-refresh/release-evidence-v1`. A remote checkout normally lacks
that ignored runtime archive, so its tracked receipt is the Git/CI release
authority. The receipt has no external signature; repository-wide correlated
resealing remains a source-control and CI trust boundary.

To regenerate after running the analyzer:

```bash
# From the repo root
python scripts/generate_web_data.py \
  --heldout-selection scripts/heldout_studies/selection-<sha256>.json \
  --heldout-labels scripts/heldout_studies/labels-<sha256>.json \
  --recall-selection scripts/heldout_studies/recall-selection-<sha256>.json \
  --recall-labels scripts/heldout_studies/recall-labels-<sha256>.json \
  --recall-report .ai-slop/state/data-refresh/end-to-end-recall-current.json
```

## Development

```bash
npm run dev          # Dev server at http://localhost:3000
npm run build        # Production build (static pages)
npm run verify:formal-release # Require local activation + archived evidence
npm run quality      # Adjudication-backed curation-consistency gate
npm run start        # Serve production build
npm run lint         # ESLint
npm run test         # Vitest
npm run test:watch   # Vitest watch mode
```

## Pages

| Route | Description |
|-------|-------------|
| `/` | Dashboard — stats cards, severity chart, monthly trend, recent vulnerabilities |
| `/cves` | Vulnerability table — filterable by severity, tool, search |
| `/cves/[id]` | Detail page — fix commits, bug-introducing commits, AI signals, LLM verdict |
| `/analytics` | Tool, severity, language, and monthly distributions |
| `/tools` | Compatibility redirect to `/analytics` |
| `/about` | Methodology, data sources, pipeline description, limitations |
